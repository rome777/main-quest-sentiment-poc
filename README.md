# PoC — 커뮤니티 글 감성분류, Gemini API 탈출

[han-river-view-or-dive](https://github.com/rome777/han-river-view-or-dive) 는
디시인사이드·코인판 등에서 암호화폐 커뮤니티 글을 모아 감성(POSITIVE/
NEGATIVE/NEUTRAL)을 분류하고, 그 결과를 매매 시그널의 입력으로 쓴다. 지금은
**Google Gemini 2.5 Flash API**가 이 분류를 전담한다 — 글 원문이 외부로
나가고, 건당 과금이며, 이 시스템에 이미 존재하는 `MockClassifier`(키워드
매칭 폴백)의 존재 자체가 이 리스크를 저자가 이미 알고 있었다는 뜻이다.

이 PoC는 그 자리에 **로컬에서 도는 한국어 특화 파인튜닝 모델**을 넣을 수
있는지 실측한다. 문제 정의부터 성공 기준까지는 [PROBLEM.md](PROBLEM.md) 를
먼저 읽어라 — 정답은 모델을 돌리기 전에 확정해 두었다.

## 무엇을 넣었나

- **문제 정의서**: [PROBLEM.md](PROBLEM.md)
- **후보 3개**를 실제 데이터로 비교했다.
  1. 지금 쓰는 방식 — Gemini 2.5 Flash API ([`poc/baseline_gemini.py`](poc/baseline_gemini.py), 프로덕션 코드를 그대로 import)
  2. 규칙 기반 키워드 매칭 — 이미 코드에 있던 폴백 ([`poc/baseline_rule.py`](poc/baseline_rule.py))
  3. `beomi/KcELECTRA-base-v2022` 파인튜닝 (MIT 라이선스, 로컬 CPU) ([`poc/finetune_kcelectra.py`](poc/finetune_kcelectra.py))
- **검증셋 20건**: 실제 DB(로컬 개발 환경, 126,506건 라벨 보유)에서 뽑았고,
  사람이 직접 정답을 확정했다 ([`poc/data/eval_set.csv`](poc/data/eval_set.csv)).
  8건은 반어법·정보 부족 등으로 일부러 어렵게 골랐다.
- **비교 결과**: [`results/comparison.md`](results/comparison.md)

## 재현 방법

```bash
# 1. 파이썬 3.12 가상환경 (torch 는 이미 설치돼 있다면 --system-site-packages 로 재사용)
uv venv .venv --python 3.12 --system-site-packages
uv pip install --python .venv/Scripts/python.exe -r requirements.txt

# 2. (선택) 원본 DB에서 다시 뽑고 싶다면 — 이미 poc/data/*.csv 로 스냅샷을 남겨뒀으니
#    보통은 건너뛰어도 된다. han-river 저장소와 로컬 PostgreSQL 이 있어야 동작한다.
.venv/Scripts/python.exe poc/extract_data.py

# 3. 후보 1 — Gemini API 실제 호출 (본인 GEMINI_API_KEY 필요, 20건이라 비용은 미미하다)
.venv/Scripts/python.exe poc/baseline_gemini.py

# 4. 후보 3 — 로컬 파인튜닝 (첫 실행 시 HuggingFace 에서 모델 다운로드, CPU로 몇 분~수십 분)
.venv/Scripts/python.exe poc/finetune_kcelectra.py

# 5. 셋을 한 번에 비교
.venv/Scripts/python.exe poc/evaluate.py
```

`poc/baseline_rule.py` 는 후보 2 자체이자 poc/evaluate.py 안에서 바로 불러
쓰므로 따로 실행할 필요는 없다.

## 결과 요약

검증셋 20건(한국어, 8건은 반어법·정보부족 등 일부러 어려운 사례), 정답은
모델을 돌리기 전에 확정했다. 전체 표와 혼동행렬, 오분류 20건 전체 목록은
[`results/comparison.md`](results/comparison.md) 에 있다.

| 후보 | 정확도 | 방향 반전 오류(POS↔NEG) | 건당 처리시간 | 외부 전송 |
|---|---|---|---|---|
| 1. 지금 쓰는 방식 — Gemini 2.5 Flash API | 13/20 (65%) | 0건 | 6.25초 | 예 (Google) |
| 2. 규칙 기반 키워드 매칭 (기존 폴백) | 7/20 (35%) | 0건 | 0.000초 | 아니오 |
| 3. KcELECTRA-base-v2022 파인튜닝 (로컬) | 12/20 (60%) | **3건** | 0.071초 | 아니오 |

**성공 기준(사전 확정)**: 14/20(70%) 이상 **그리고** 방향 반전 오류 2건 이하.

## 개선 효과 검증 — 결론: 이번 파인튜닝 구성은 기준 미달, 채택하지 않는다

파인튜닝 모델은 정확도(60% < 70%)와 방향 반전 오류(3건 > 2건) **둘 다**
기준을 못 넘었다. 이것도 유효한 PoC 결과다 — "지금 방식이 낫다"가 나온
경우다. 이유를 뜯어보면:

- 3건의 방향 반전(#4, #5, #7)은 모두 **비속어·거친 어조가 낀 문장**이다.
  `아래에서 탄 새끼들 지금 좆도 안쫄리면서 ㅅㅂ`(자신감 있는 긍정)을 부정으로,
  `스토리지 잘가세요~~`(조롱조 작별=부정)를 긍정으로 뒤집었다. 학습 데이터가
  Gemini 라벨을 그대로 베낀 실버 라벨 2,676건뿐이고 사람이 다시 검수하지
  않았다 보니, 모델이 "비속어 = 감정 강도" 정도만 배우고 그 비속어가
  향하는 대상(시장이냐 사람이냐, 긍정적 맥락이냐 조롱이냐)까지는 못
  잡아낸 것으로 보인다.
- 오히려 파인튜닝 모델이 Gemini보다 잘 잡은 것도 있다. #13(매매할게 없다),
  #17(기분좋게 점심먹으려하는데)처럼 **정보가 부족해 NEUTRAL이 맞는 사례에서
  Gemini는 섣불리 방향을 단정했지만 파인튜닝 모델은 정확히 맞혔다.**
  즉 "확신 낮으면 중립"이라는 패턴은 어느 정도 배웠다.
- 규칙 기반(35%)은 그대로 "확인용 기준선" 역할을 했다. 코드에 박힌
  키워드 목록(가즈아·떡상·한강·폭락 등)이 이 커뮤니티가 실제로 쓰는 말
  (숏·청산·포모·개추·설거지)과 거의 안 겹쳐서, 20건 중 18건을 그냥
  NEUTRAL로 찍었다. "이미 있는 규칙 기반 방법은 이 도메인에서 쓸모가
  없다"는 것도 이번에 확인한 사실이다.

## 뜻밖의 발견 — 지금 쓰는 방식(Gemini)의 신뢰성 문제

이번 PoC에서 가장 중요한 발견은 사실 정확도 숫자가 아니다. **Gemini
API가 20건 중 2건(10%, #4·#19 — 둘 다 반어법이 낀 "어려운" 사례)에서
5번을 재시도해도 계속 JSON이 중간에 끊겨서 파싱에 실패했다**
(`{"label": "POSITIVE"...` 가 35글자쯤에서 잘리는 식). 프로덕션 코드
(`hanriver/llm/client.py`)의 재시도 로직(`_is_retryable`)은 429/5xx만
재시도 대상으로 보고 이런 파싱 실패는 재시도하지 않는다 — 즉 **지금
운영 중인 시스템은 바로 이런 어려운 글에서 그 잡을 그냥 실패 처리하고
넘어가고 있을 가능성이 높다.** 반어법이 많이 섞인 글일수록 감성 신호가
더 중요한데, 정작 그런 글에서 조용히 유실되고 있다는 뜻이라 후속 조치가
필요하다. (별도 이슈로 분리했다 — 이 PoC 저장소의 범위 밖이라 여기서
고치지 않았다.)

## 한계와 다음 단계

- **정답 신뢰성**: 검증셋 20건의 정답은 나 혼자 판단했다. 실제로는
  여러 사람이 라벨을 매기고 일치도(inter-rater agreement)를 재는 것이
  정석이다.
- **본문 없이 제목만**: `raw_post.body` 가 항상 비어 있어(백필 설계)
  제목 한 줄만으로 분류한다. 정보가 원래 부족한 상태에서 시작한다.
- **학습 자료가 다른 모델(Gemini)의 판정을 베낀 것**: 사람이 검수한
  정답이 아니라 실버 라벨이라, 파인튜닝 모델은 원리상 Gemini의 오류까지
  같이 배울 수 있다. 그런데도 위에서 보듯 실제로는 Gemini와 다른 방향으로
  틀리기도 했다 — 완전히 같은 오류를 복제하지는 않았다는 뜻이다.
- **영어 글 제외**: 4chan·Reddit(영어)은 이번 범위 밖이다. 이 시스템이
  실제로 영어 소스도 쓰므로, 로컬 모델로 완전히 대체하려면 영어 경로는
  별도 후보(예: 다국어 사전학습 모델)가 필요하다.
- **다음 단계 후보**:
  1. 학습 자료를 검증셋만큼 사람이 직접 검수한 라벨로 늘린다(지금 2,676건
     중 표본만이라도).
  2. 얼리는 층 수(`UNFROZEN_LAYERS`)를 늘리거나 학습 데이터를 키워
     방향 반전 오류부터 줄인다 — 이게 이번 결과에서 가장 치명적인 항목이었다.
  3. Gemini의 JSON 파싱 실패를 별도 이슈로 고친다(재시도 대상에 `ParseError`
     추가) — 이건 PoC 결과와 무관하게 지금 당장 고칠 가치가 있는 버그다.
  4. 데이터가 늘어나면(수만 건 규모) 임계값 기반으로 "확신 없음"을 걸러
     사람 검수로 넘기는 3번째 선택지도 열려 있다(강의 4강의 SigLIP 임계값
     구간 찾기와 같은 방식).
